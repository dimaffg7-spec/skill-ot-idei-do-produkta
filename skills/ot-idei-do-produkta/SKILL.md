# От идеи до продукта

Ты ведёшь человека по маршруту: **идея → архитектура → код**. Порядок не нарушается.
Архитектура рождается из идеи, план из архитектуры, код из плана. Никогда не сразу в код.

**Вход.** Замысел, описанный словами, плюс папка - пустая или с готовым кодом.
**Выход.** Работающий код в отдельной ветке, никуда не отправленный, и папки `idea/`
и `architecture/`, по которым видно, что и почему построено.

Все промпты маршрута - в `references/`. **Промпты подставляются дословно, не пересказываются
своими словами.** Формулировки выверены: пересказ ломает точность вопроса,
а с ней и ответ.

---

## Первое, что делаешь: определяешь ветку

| Признак | Ветка |
|---|---|
| Папка пустая, кода нет | **новый проект** - обычный маршрут |
| Есть `package.json`, каталог с исходниками или коммиты в git | **живой код** - сначала `references/razvedka.md` |

В ветке живого кода разведка идёт до первого вопроса человеку: четыре читателя строят карту
проекта, снимают паспорт среды и базовую линию. Замысел не сочиняется заново, а
восстанавливается из кода с пометками «из кода / со слов / догадка».

---

## Маршрут

| Этап | Шаги | Что появляется | Файл со справкой |
|---|---|---|---|
| Разведка *(только живой код)* | - | `architecture/00-karta-proekta.md`, `00-passport.md` | `references/razvedka.md` |
| Дом проекта | 3.1-3.2 | папка проекта, `CLAUDE.md`, `business/` | `references/01-ideya.md` |
| Идея | 3.3-3.14 | `idea/` - до 9 файлов | `references/01-ideya.md` |
| **Развилка** | - | решение: архитектура нужна или нет | этот файл, ниже |
| Архитектура | 5.0-5.10 | `architecture/` - файлы 01…10, `schema.prisma` | `references/02-arhitektura.md` |
| **Приёмка архитектуры** | - | вердикт «можно в код» | `references/priemka-arhitektury.md` |
| Код | по фазам плана | код в ветке, коммиты | `references/03-kod.md`, `references/gates.md` |
| Урок | - | запись, что выучили | этот файл, ниже |

Контекст и нарезка на сессии - `references/sessii.md`. Читается перед первым длинным этапом.

## Развилка: нужна ли архитектура

Решается автоматически, в конце идеи - раньше не на чем решать, позже план уже написан.
Критерий - четыре признака:

1. Настоящие пользователи, кроме автора?
2. Задеты деньги?
3. Персональные данные людей?
4. Проект живёт дольше месяца?

**Любое «да» - архитектура обязательна.** Все «нет» - разовый инструмент, идём сразу в код,
архитектура для скворечника не рисуют.

Решение объявляется вслух, с причиной, и человек может отменить его одной фразой:

```
Идея разобрана. Архитектура: НУЖЕН.
Почему: появляются две новые сущности, задеты деньги, проект живёт дольше месяца.
Не согласен - скажи «без архитектуры», пойду сразу в код.
```

**Глубина идеи - той же развилкой.** Все «нет»: только `superidea`, `proof-of-value`,
`risks`, `mvp`. Хотя бы одно «да»: все девять файлов, включая необязательные
(3.5 why-now, 3.6 references, 3.7 deep-research, 3.10 principles, 3.12 vision).

**Пересмотр - один раз.** Если по ходу выяснилось, что задача крупнее, вернуться и сказать
«беру назад, архитектура нужна» можно ровно один раз, иначе прогон крутится по кругу.

## Пять остановок, других нет

Между ними человек не участвует - только смотрит. Наткнулся на шестую причину спросить -
это находка строкой в отчёт, а не новый вопрос.

1. **Идея собрана** - показать целиком, дождаться «да». Раньше автономная часть не стартует.
2. **Архитектура принят или нет** - показать результат приёмки, семь вопросов.
3. **План утверждён** - показать фазы и признаки готовности.
4. **Первый коммит** - право на него подтверждается явно, один раз за проект.
5. **Выкатка** - никогда не делается сама. Показать команду и последствие, кнопку не жать.

## Что не делается никогда

Работа доводится до готовности, последний шаг остаётся человеку:

- код уезжает за пределы локальной копии: push в основную ветку, деплой, применённая миграция;
- что-то начинает само писать живым людям: письма, сообщения, уведомления;
- задеты деньги, доступы, удаление данных.

Плюс жёсткие правила из `references/gates.md`: `git add` поимённо, реальный `.env` не читать,
перед push - сборка, удаление - только с показом, что удаляется.

## Урок в конце

После того как код работает, прогоняется цикл из пяти ходов - не пропускается:

1. Найди ошибки в написанном коде, докажи примером, исправь.
2. Что упустили: граничный случай, проверка ввода, обработка ошибки.
3. Это реально проблема этого проекта? Сверь с `business/` и планом.
4. Перечитай изменения свежим взглядом, как будто видишь впервые.
5. Персональные данные, чужой контент, отправка наружу - есть хоть одно, стоп и разбор.

Дальше короткая запись: что сделали, что не получилось, что поняли. Если ошибка повторяемая -
правило в `ai-clone/feedback/` по канону «что делать → почему → когда срабатывает».

## Когда НЕ звать

Правка в один файл · переименование · строка в настройках · разовый скрипт · отдельная
задача внутри уже готового плана · «перепиши этот модуль» - там нет ни боли, ни человека,
которому болит, а на этом стоит вся идея.

Маршрут длинный по устройству. На мелочи он дороже и медленнее, чем сделать руками.
