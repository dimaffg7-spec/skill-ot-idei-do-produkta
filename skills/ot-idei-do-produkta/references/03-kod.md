## Шаг 6.1 - Защита проекта + правила из архитектуры

**Промпт · защита + правила из архитектуры**

```
Включи в моём проекте защиту и перенеси правила из архитектуры. Проект живёт с прошлых модулей: CLAUDE.md, business/, idea/, architecture/, plans/, retrospectives/ и git уже есть - ничего из этого заново не создавай и не дублируй.

1. Перенеси в CLAUDE.md нерушимые правила проекта из architecture/00-правила-проекта.md. ОБЯЗАТЕЛЬНО впиши: код пишется по architecture/, замысел - в idea/, агент читает их перед каждой задачей.

2. Создай папку prompts/ (библиотека проверенных промптов проекта) - пока пустую, с README в одну строку.

3. Включи защиту сразу:
- запреты опасных команд в .claude/settings.json (если файла нет - создай);
- pre-commit-хук против секретов (ставится в .git/hooks/pre-commit, делается исполняемым), чтобы случайный .env или ключ не ушёл в коммит;
- хук PostToolUse, который после каждой правки кода автоматически гонит сборку, линт и тесты моего стека;
- проверь, что .gitignore на месте и в нём .env (мы заводили его в Модуле 5).

Покажи итоговый CLAUDE.md и список того, что добавил. По одному вопросу за раз, если чего-то не хватает - спроси и жди, не выдумывай. Отвечай на русском.
```

## Шаг 6.4 - База из схемы (первая миграция + seed)

**Промпт · база + seed**

```
Подними базу из схемы, спроектированной в architecture/ (например prisma/schema.prisma), под МОЙ стек.

1. Сначала сними состояние окружения (что установлено, что нужно - например Docker для локальной базы). Если чего-то не хватает - проведи меня по установке по одному шагу. Потом перенеси схему в рабочее место и примени как первую миграцию:
- Node/Prisma: schema.prisma -> миграция init + генерация клиента
- Python: модели + первая миграция (makemigrations / alembic)
- Go/другое: SQL-миграция мигратором стека
- Low-code: создай таблицы по схеме
Локальную базу подними одной командой, строку подключения положи в .env.

2. Создай seed с МИНИМУМОМ синтетики под срез на сегодня. Идемпотентный (upsert), повтор не плодит дубли.

3. Если задача и нерушимые правила из architecture/ расходятся в чём-то (например в формате хранения денег) - НЕ решай молча: покажи мне конфликт и предложи, как правильнее под мой проект и моих пользователей, как если бы решал сам и тебе потом с этим работать.

Соблюдай нерушимые правила и правила миграций. Покажи данные глазами. По одному вопросу за раз. Отвечай на русском.
```


## Шаг 6.5 - Сквозной срез test-first (главный шаг)

**Промпт · сквозной срез (test-first)**

```
Работаем test-first. Сначала ОДИН приёмочный тест, потом код под него. Стек мой - см. CLAUDE.md.

1. Тест из главного сценария приёмки (plans/<ГГГГ-ММ-ДД>-vertical-slice.md): бьёт в тестовую базу, проверяет, что после действия запись появилась в нужном статусе. beforeEach чистит и ре-сидит базу. Сейчас тест КРАСНЫЙ - так и надо.

2. Минимум кода, чтобы тест позеленел, строго по раскладке из architecture/: одна страница с формой -> одно серверное действие (создаёт запись с начальным статусом) -> список записей на той же странице. Весь срез держи рядом по вертикали.

3. Гоняй тесты после каждой правки. Красный тест - стоп-кран. Покажи зелёный прогон. Отвечай на русском.
```


## Шаг 6.7 - Экран статуса + проверка полного круга

**Промпт · экран статуса + проверка круга**

```
1. Сделай одну поверхность статуса под мой стек: читает записи пользователя и показывает их статусы (pending / processing / done / failed). Для веба - серверная страница со списком и бейджами, цвета из бренд-гайдлайнов проекта, «живость» через повторный запрос раз в несколько секунд. Для бота/CLI/фона - ответ в боте, вывод в консоль или строка в лог.

2. Проверь полный круг (форма/команда -> pending -> воркер -> done -> статус сменился). Для веба - через Playwright: открой страницу, заполни форму, отправь, дождись записи, сделай скриншот «до» и «после». Если Playwright не подключал или экрана нет - используй /verify: собери, запусти, пройди круг как пользователь и доложи результат.

Отвечай на русском.
```


## Шаг 6.8 - Цикл 5 ходов: не принимаю код на веру

**Промпт · цикл 5 ходов**

```
Я не принимаю код на веру. Прогони пять ходов по последним изменениям.

Ход 1. Найди ошибки свежим взглядом: off-by-one, null, краевые случаи, гонки, утечки, нарушения нерушимых правил. Нет ошибок - назови 3 места, где сломается при росте в 100 раз, и спроектируй так, чтобы мощности можно было нарастить бесшовно: маячок, который заранее предупреждает (нагрузка / длина очереди / скорость / размер базы перевалили порог), пока ничего не упало. (усиление: /code-review high --fix)

Ход 2. Что упустили: сценарии, пограничные случаи, зависимости, что будет через месяц. По каждому - почему упустили.

Ход 3. Докажи, что это РЕАЛЬНО проблема в нашем проекте (продукт, аудитория, десятки пользователей, приоритет «запустить»). Перфекционизм - вычеркни.

Ход 4. После правок свежим взглядом: что появилось новое, что могли сломать (прогони ВСЕ тесты).

Ход 5. Security review: опасная тройка, инъекции, утечки токенов, .env, права на эндпоинтах, rate limiting, валидация. (усиление: /security-review)

Отвечай на русском.
```
